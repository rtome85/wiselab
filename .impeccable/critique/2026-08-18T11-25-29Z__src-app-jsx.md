## Design Specificity Verdict

**LLM assessment**: Grounded, not generic. The locked-skeleton/active/completed stepper *is* the step-gating mechanism, not decoration painted over a chat log — the "Next step" button is functionally blocked by `challengeCompleted` state, matching PRODUCT.md's positioning claim exactly. The coral/seafoam split is disciplined in the actual code (grep-confirmed), not just documented. This is a stronger-than-average identity-to-mechanism match.

**Deterministic scan**: `detect.mjs` found 11 findings across `src/`: 9× `design-system-font-size` (a `text-[10px]` literal used consistently for badge numbers/timestamps/icon glyphs — off DESIGN.md's documented ramp, which has no step below 12px), 1× `overused-font` (Inter at 100% of text — expected given DESIGN.md's deliberate single-sans-font system, not a specificity flaw), 1× `design-system-radius` (`.skeleton`'s `border-radius: 4px`). On verification, this last one is a **real, confirmed contradiction**: DESIGN.md's `rounded` scale has no step below 8px, and its Shapes section states explicitly "nothing in the system uses a sharp 0–4px radius" — Assessment B mistakenly attributed a `rounded.xs: 4px` token to justify it, but that key is under the `spacing` scale, not `rounded`. The skeleton bars are the one place the implementation quietly breaks the system's own documented radius floor.

**Visual overlays**: Browser injection succeeded; overlays are not currently live in a tab (the sub-agent's session ended), but the findings below are drawn from its screenshots and console output.

Confirmed **false positives** from the detector, both in the overlay and CLI passes: the "disabled Generate button" low-contrast flags (white text on coral/coral-gradient tokens) — the detector reads the pre-opacity token color rather than the composited `disabled:opacity-30` render, and disabled controls are exempt from contrast requirements anyway. Also false positive: the `ai-color-palette` ("cyan neon on dark") and `dark-glow` flags in dark mode — these pattern-match against DESIGN.md's own deliberately documented dark-mode Seafoam Calm value (`#69d6f5`) and the named CTA-glow rule; both are confirmed, intentional brand tokens from the Pencil design frames, not generic AI-slop coloring. One `nested-cards` flag is also a likely false positive (the Settings segmented control, a documented, intentional pill pattern); a second `nested-cards` instance and the 5× `body-text-viewport-edge` mobile-dark flags could not be fully isolated from overlay-induced artifacts in the time available — flagging as unverified rather than confirmed.

**Real, confirmed contrast failures** the LLM review didn't quantify: two teal-on-background pairs fail WCAG AA for normal text — `#26a9a7` (Seafoam Calm) on `#f8fbfc` (app background) at **2.8:1**, and `#26a9a7` on `#ddf5f3` (accent-soft) at **2.5:1**, both well under the 4.5:1 minimum. These aren't decorative — the app-bg pairing includes the "AI TUTOR" eyebrow label on the hero screen, the very first piece of brand-colored text a new visitor sees. Two near-misses are also worth a look: muted text (`#6d7a89`) on both surface and app backgrounds lands at 4.4:1 and 4.2:1 — just under the 4.5:1 line.

## Overall Impression

The core mechanism is well-built and true to the product's positioning — the stepper, the gating, the restrained coral/seafoam discipline all hold up under both an independent design review and a mechanical scan. But polish drops exactly at the highest-stakes moments: the very first thing a new user sees (the missing-API-key banner) breaks the system's own color rules and its light/dark parity promise, and the moment a student is genuinely stuck (wrong challenge answer, a real API error) gets the least design attention of any state in the app. There's also a real product/implementation gap: PRODUCT.md's Operating Context describes a subject-selection step (math/physics/chemistry) that does not exist anywhere in the shipped UI — worth resolving one way or the other.

## What's Working

1. **The locked-skeleton stepper encodes the product's actual promise.** A student can see "there are 6 steps" without any of them being spoilable — the anti-shortcut mechanism PRODUCT.md describes is the UI, not an illustration of it.
2. **The Single Ignition Rule holds in practice.** Coral stays confined to CTAs and the active-step glow; Seafoam stays confined to focus/informational state — confirmed both in source and live, in both themes.
3. **Light/dark token parity is real for the primary flow.** Idle screen, drawers, and input card all hold up correctly in both themes with intentionally-tuned (not auto-inverted) values — the one place this discipline breaks is the warning banner (below).

## Priority Issues

**[P1] Missing-API-key banner breaks the system's own color rules and light/dark parity**
**Why it matters**: This is the first screen a new, no-key-configured visitor sees. In light mode it's `bg:#ffffff`/`border:#e6edf1` — visually identical to a plain flat card, easy to skim past. In dark mode it becomes a saturated burnt-orange fill with a border nearly identical to dark-mode Coral Spark. It introduces a bespoke fifth semantic hue (`--color-warning-*`) that DESIGN.md's own Locked-Palette Rule forbids, and the light/dark treatment is inconsistent rather than tuned-per-theme like everything else.
**Fix**: Map the missing-key state onto the existing `error` (red) semantic at balanced opacity in both themes; remove the bespoke `warning-*` tokens.
**Suggested command**: `/impeccable harden`

**[P1] Confirmed WCAG AA contrast failures on Seafoam Calm text**
**Why it matters**: `#26a9a7` on `#f8fbfc` (2.8:1) and on `#ddf5f3` (2.5:1) both fail the 4.5:1 minimum for normal text — measured, not estimated. This lands on real, visible UI: the hero "AI TUTOR" eyebrow label and accent-colored links/badges, not decorative chrome.
**Fix**: Darken the light-mode Seafoam Calm token (or restrict it to large/bold text ≥3:1 contexts) until both pairings clear 4.5:1; re-verify the two near-miss muted-text pairs (4.2–4.4:1) while in there.
**Suggested command**: `/impeccable audit`

**[P1] No recovery path at the exact moment a student is stuck**
**Why it matters**: A wrong challenge answer produces only a red highlight and a bare "Try again" — no nudge toward the "I'm confused" chat sitting a few pixels below in the same card. A generic API/network/malformed-response error all render identically as a raw string in a red card. For a product whose entire positioning is "understanding over answers," the failure moments get the least scaffolding of any state in the app.
**Fix**: After a wrong attempt (especially a second one), surface an inline prompt into the confused-chat with the challenge context pre-loaded; differentiate error copy by cause (bad key / network / malformed response) instead of showing the raw error string.
**Suggested command**: `/impeccable clarify`

**[P2] PRODUCT.md describes a subject-selector that doesn't exist in the shipped UI**
**Why it matters**: PRODUCT.md's Operating Context states the student "picks a subject (math/physics/chemistry)" — but no subject-picker component exists anywhere in the current app (confirmed via source search). Either this is stale documentation or a real control was silently dropped. A student with an ambiguous problem (e.g., a "rate of change" question readable as math or physics) has no way to disambiguate before generating or to correct a wrong inference afterward.
**Fix**: This is a product-truth question before a design one — confirm whether subject selection should exist, then either add a lightweight picker or correct PRODUCT.md.
**Suggested command**: `/impeccable shape`

**[P2] Duplicate hand-rolled drawers with inconsistent accessibility, while a working primitive sits unused**
**Why it matters**: `ui/Sheet.jsx` (Radix Dialog — built-in focus trap, portal, ARIA wiring) has zero references anywhere else in the codebase. `HistoryDrawer.jsx` and `SettingsDrawer.jsx` each hand-roll backdrop/Escape/scroll-lock instead, and diverge: `SettingsDrawer` implements a manual Tab-cycle focus trap and restores focus on close; `HistoryDrawer` does neither, so a keyboard user tabbing through open history can tab straight into the dimmed background content.
**Fix**: Migrate both drawers onto `ui/Sheet.jsx` and delete the duplicated logic, or port `SettingsDrawer`'s focus-trap into `HistoryDrawer`.
**Suggested command**: `/impeccable audit`

## Persona Red Flags

**Jordan (First-Timer)**: Lands on idle, sees the API-key banner but — in light mode especially — it barely reads as urgent (flat white, hairline border indistinguishable from page chrome). No onboarding explains *why* steps are locked before Jordan hits the first skeleton card; it could easily read as a loading bug rather than an intentional mechanic.

**Sam (Accessibility)**: Two source-confirmed issues plus one measured one: (1) `ProblemInput.jsx`'s image-remove button has a hard-coded `aria-label="Remover imagem"` (Portuguese) regardless of active language — every other string in that file correctly routes through `t()`, and `en.js` already has an unused `image.remove` key sitting right there; (2) `HistoryDrawer` has no focus trap while `SettingsDrawer` does, so keyboard-only navigation is inconsistent between the two overlays; (3) the Seafoam-on-background contrast failures above (2.5–2.8:1) mean Sam may not be able to read the hero eyebrow label or accent links at all, independent of any assistive tech.

**Riley (Stress Tester)**: `ProblemInput.jsx`'s `handleFileChange`/`handleDrop` iterate unbounded over dropped files with no cap or queueing — a 20-photo drop would fire 20 concurrent OCR calls with zero rate-limit UI. Unverified live (requires a working API key) but confirmed at the source level.

**Casey (Mobile)**: Layout reflows cleanly at 390px with no horizontal scroll. The `⌘↵` shortcut hint area goes fully blank on mobile (`hidden sm:flex` with an empty sibling div) — a wasted slot where a mobile-relevant hint could live. The 5 flagged `body-text-viewport-edge` overflow instances in dark-mode mobile need manual re-verification — some may be overlay-obscured artifacts rather than real overflow, per Assessment B's own caveat.

**Amara (project-specific — international self-directed student, per PRODUCT.md)**: Opens WiseLab for the first time in French, hits the BYO-key wall (expected, documented architecture). If she gets past that with an ambiguous problem, she has no subject-picker to disambiguate or correct a wrong AI inference — see the P2 product-drift issue above.

## Minor Observations

- 9 instances of a `text-[10px]` literal (badge numbers, timestamps, small icon glyphs) sit below DESIGN.md's documented type ramp floor of 12px — consistent enough across the codebase to look like a deliberate micro-label size that was simply never documented, not drift. Worth adding a `micro: 10px` step to DESIGN.md if it's staying, or bumping instances to the existing 12px `label` size if not.
- `.skeleton`'s `border-radius: 4px` (`src/styles/index.css:92`) is the one place the implementation contradicts DESIGN.md's explicit "no sharp 0–4px radius" rule — bump to the 8px `control` radius or add a documented exception for skeleton bars specifically.
- DESIGN.md itself has an internal contradiction: the general Colors section assigns "badges" to Seafoam Calm, but the Step Card signature-component section describes the completed-step badge as "a filled Coral-badge checkmark." The code sided with Seafoam (the more Single-Ignition-Rule-consistent choice) — worth reconciling the doc language, not a code defect.
- `constants/settings.js`'s `DEFAULT_SETTINGS.language` is `'PT'` but only applies when a returning user has stored settings; fresh visitors correctly get `detectBrowserLanguage()`. The constant's name is just misleading.

## Questions to Consider

1. If the product's whole positioning is "understanding over answers, protected by gates," why does a wrong challenge answer produce *less* scaffolding than a right one — shouldn't failure be exactly where the confused-chat steps forward automatically instead of waiting to be discovered?
2. PRODUCT.md still describes subject selection as part of the flow, but the shipped UI has none — was that an intentional simplification (let the AI infer it), and if so, what happens to a student's trust when the inferred subject is visibly wrong and uncorrectable?
3. The API-key-missing banner is arguably the single highest-stakes screen in a BYO-key, no-backend product — it's the one moment where unclear communication costs a student the entire product. Why does it use a bespoke, undocumented color pair instead of the `error` semantic DESIGN.md already locked in for exactly this kind of blocking state?
